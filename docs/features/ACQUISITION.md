# Local file acquisition

The Windows Core copies selected source files to an existing local destination. It never renames or deletes the source during acquisition. A separate destination receives a new resource folder; an occupied output folder is rejected. If the canonical destination equals the source folder, the task uses existing files without a duplicate copy. This is the local-Core path. Remote Core downloads and a separate desktop transfer agent remain unimplemented.

## Preview and submit

An authenticated desktop obtains `GET /api/resources/{id}/acquire-preview`. The response includes `files` (`id`, absolute `path`, `relative`, `size`, `archive_entry`), total `bytes`, known `volume_groups`, `source_folder`, and `manifest_digest`. Relative paths are computed from the entire resource, including any known sibling volumes from older catalogs.

Submit `POST /api/acquire` with `resource_id`, `destination`, `file_ids`, `manifest_digest`, optional `extract`, and optional `password`. The HTTP endpoint requires the reviewed manifest even when all files are selected. Empty, duplicate or unrelated file IDs, an outdated manifest, and a partial known volume group are rejected before a job is created. Selecting a subset does not bypass missing/unverified resource-member checks.

The manifest digest covers resource identity and the ordered file IDs, paths, sizes and modification times. It detects catalog changes; it is not a full-content hash or proof that an executable is runnable. Selected files are checked against their current filesystem metadata before queueing and again during copying. A changed file requires a new scan and preview. Known multipart groups additionally undergo a full archive test before publication, including copy-only transfers.

## Existing local files and device defaults

**Preparation method → Use existing files** submits the reviewed selection with its source folder as destination. Core also recognizes this case when the same folder is entered manually. It rechecks selected paths, file sizes and modification times when queued, on execution/resume, and after any multipart verification. The job records `reuse_existing: true`, reports zero copied bytes and completes with `Using existing files at ...`. No staging tree, duplicate resource folder, extraction or game launch is performed. Missing/unverified files, changed sources, invalid selections and incomplete volume groups still fail; passwords for encrypted volume verification are provided again on retry.

Extraction requires a separate destination. In-place extraction is rejected before queueing so generated files cannot be mixed into the source. Old jobs without `reuse_existing` retain copy behavior. This is an additive job-spec field, not a database schema migration.

**Save as default**, **Use default** and **Clear default** manage the destination in frontend-local storage on the current device. Saving a default does not start a task. A one-off destination change does not overwrite the saved value. Storage failures are shown explicitly. The default path is not part of catalog backup or restored catalog state; Core validates the selected folder when submitting each task.

## Copy, extract and recover

The durable job stores its exact selected members and the original member count. A partial copy reports `Selected N of M source files` on completion. Member paths preserve the full resource layout: selecting only `extras/readme.txt` still produces `extras/readme.txt`.

Copying uses a per-job staging directory and resumes partial files only after comparing their saved prefix with the source. Complete staged files are also checked before reuse. Cancellation and pausing leave the source intact. The current archive extraction restarts on resume; passwords are provided again and are never stored in the job or command line.

New jobs extract each archive beside its copied file into `<full archive filename>-extracted`. For example, `base/game.zip` and `extras/game.zip` produce separate extraction folders. Source-file conflicts with these folders are rejected. Older queued jobs preserve their previous extraction checkpoint paths. This selection UI selects source files, not individual entries inside a compressed archive.

Publication uses a no-replace move and a persisted receipt containing all output file hashes. After interruption, an existing final directory is accepted only if it matches that receipt. Acquisition does not overwrite an existing destination or silently merge a later selection into it.
